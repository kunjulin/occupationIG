M-6　第 19 條保存期限　✅ 不列入本指引範疇（已界定）

界定（0.3.0，JOB-26）　《勞工健康保護規則》第 19 條之保存期間，係各事業單位與 醫療機構依法自行辦理之行政義務，與「健檢資料如何在機構間交換」無涉。本指引之職責為 規範資料結構與交換方式，不以資料欄位承載法定保存期限，亦不對其起算點作成解釋。

為何是界定而非迴避　起算點採「檢查日」「報告日」或「勞工離職日」尚無定論，三者對同 一筆紀錄可產生數年差異。在法律解釋確定前將保存期限結構化進資料欄位，等於把一個未定 的解釋寫死進規範——其代價高於不做。本指引原即「未於資料層固定任一解釋」，該判斷正確， 惟先前列於待決清單，易被誤讀為未完成之工作項目，故改標為範疇界定。

與同類事項之一致性　本項處置與存取控制政策（見 M-10）採同一原則： 法規與機構政策層面之決定不納入資料規格。臺灣核心實作指引之〈安全性〉頁亦明載 「所使用的策略和方法不在此規範的範圍內」，本指引比照辦理。

實作端須知　保存期限仍應依法遵循，僅係不由本指引以結構化欄位承載； 各機構得依其資訊系統既有機制辦理。

出處　background.md §3.1.1

M-10　稽核與同意機制之選型

本項已於 0.3.0 縮小範圍（JOB-27）。 原標題為「雇主端資料隔離之實作機制」， 易被誤讀為揭露範圍未定。實際上揭露範圍已定案，未定的只有稽核與同意之機制選型。

已定案，不在本項範圍內　雇主端可取得之資料範圍已定案且可驗證：雇主端使用 TWHA-Composition-EmployerSummary， 其 section 採 closed slicing，結構上保證不含檢驗 section。雇主端封包若宣告符合 該 profile 卻夾帶檢驗數值，驗證器會擋下來——這不是原則宣示，是可驗證的結構約束。 詳見安全與個資保護 §2.2。

亦不在本項範圍內　誰可以存取屬存取控制政策，依法規與機構政策辦理， 不在本指引範圍——見 security.html §0 之範疇聲明。

本項所指之待決　僅限稽核與同意之 FHIR 機制選型： Consent／Provenance／AuditEvent／SMART scope 各自之角色與最小實作要求， 以及是否納入本期範圍。

技術設計建議（非政策決定）　建議之最小可稽核組合為 Consent（同意依據） ＋ AuditEvent（存取軌跡），並以 SMART scope 表達授權範圍。此為技術設計建議， 供主管機關與平台端採認，非本指引之政策認定。

所需輸入　主管機關與平台端之架構決定。

影響範圍　security.md；可能新增 profile。

若決策不同　僅有原則宣示而無可驗證之稽核機制，實作端各行其是，存取軌跡無法勾稽。 惟揭露範圍本身不受影響——該部分已由 profile 結構保證。

出處　security.md；JOB-11；JOB-27

G-2　驗證結果之意義界定

這不是待決事項，是一項永久性聲明。

IG Publisher 驗證通過僅證明語法正確，且已被引用之術語通過代碼有效性檢查。 它不包含：

  • 臨床適切性；
  • 法規符合性；
  • 情境完整性；
  • 未被任何 profile／ValueSet 引用之對照表代碼。

不得以「0 Error」或任何 QA 統計作為本指引整體品質之表述。

出處　README.md、index.md

G-3　建置驗證不檢查 display 語意

這是已知盲區，非待決事項。

IG Publisher 只檢查「代碼是否存在於該 CodeSystem」，不檢查 display 是否與代碼 真實語意相符，且該訊息僅為 INFORMATION 等級。因此語意完全錯誤的代碼可一路通過 0 Error 建置。

實例：14390-9 曾於本指引標為「ALT」，LOINC 官方為 「Amylase [Enzymatic activity/volume] in Dialysis fluid」（透析液澱粉酶）。

⚠️ 另一個相關盲點　IG Publisher 摘要行的 err 計數不含斷鏈區段。 目前有 2,078 筆斷鏈未被 err 涵蓋（其中 2,026 筆見 P-1）。

預設規則（0.3.0，JOB-26 定案）　預設採 (a)：維持 TW Core 繼承， 非檢驗類結果之承載方式另以 implementation note 說明。

為何不採 (b)　為單一議題脫離母規範繼承，將失去 TW Core 對本指引之一致性保證， 且與本案「不修改核心、加掛擴充」之基本設計相違；其代價高於本議題之效益。 俟 TW Core 維護團隊就 result 約束意圖答覆後再行評估。

待決（續辦）　健檢報告之彙整資源選擇：(a) 維持現狀——DiagnosticReport.result 僅收檢驗項目，其餘一律走 Composition；(b) 本 IG 對 result 放寬型別—— 但 FHIR profile 不得放寬上游約束，此路徑需改為不繼承 TWCoreDiagnosticReport； (c) 向 TW Core 提案放寬。

所需輸入　TW Core 維護團隊對 result 約束意圖之說明；平台端對 「報告容器」之實際需求（僅檢驗？或含全部健檢項目？）。

影響範圍　TWHA-DiagnosticReport；example-diagnostic-report； general-exam.md 之報告章節；上傳封包之組成建議。

若決策不同　若採 (b) 脫離 TW Core 繼承，將失去 TW Core 對 DiagnosticReport 之全部約束與互通性主張，代價大於效益，除非 TW Core 明確表示 result 之限縮並非有意。在此之前，實作端不應把非檢驗 Observation 塞進 result——那會在上游驗證失敗。

出處　JOB-05 補範例時之 CI 實測（run 30406136544）

T-13　口腔黏膜檢查表之 6 選 1 級距未取得原文　✅ 已解決（0.4.0）
